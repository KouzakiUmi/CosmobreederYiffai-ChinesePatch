# batch-25：改文案让折行不切词

## 为什么换办法

batch-23 用插 U+2028 的办法修了 1,163 行的切词，剩下的 197 处修不动——任何挪动都会在别处挤出一个新切词。batch-24 试过一轮「只修最严重切词、分页不动」，41 行全部是「把一处切词换成另一处」，整批回退。

结论是：**在不改分页的约束下，插断行符修不了切词**。所以这批换办法——**改文案**。

用户已明确：翻译本来就可以适当润色，允许重写整句只要意思不变，分页变了也可以。

## 做法

把「折行会切开常用词」的行全部找出来（96 行），逐条对照英文原文重写中文，让断点自然落在词边界。

三条硬条件：

1. **意思与英文一致**，不删信息、不加原文没有的内容；
2. **原来的切词消失**，且**不引入新的切词**（任意两行交界处不能切开常用双字词）；
3. **每行不超过 240px**，按 `story12` 真实字模验算。

## 规模

96 行，但只有 **45 组不同（英文，旧文）**——同一句在多处重复（「其他特工绘制了你所在区域各部分的地图」出现 34 次）。改写 29 条覆盖 96 行。

| 项 | 数量 |
| --- | ---: |
| 目标行 | 96 |
| 改写成功 | 96（零失败） |
| 引擎实测：仍占 1 页 | **96 / 96（分页次数不变）** |

显示行数（引擎实测，非空行）：改前 2 行 55 例、3 行 41 例；改后 1 行 4 例、2 行 74 例、3 行 18 例。

**分页次数没有变化**——96 例改前改后都是 1 页。变的是这一页里占几行，不是翻页。

## 顺带消掉的译法分叉

同一句英文在这 96 行里有三种不同译法：

```
其他特工绘制了你当前所在区域各部分的地图，有时还带标注。      x12
其他特工已经绘制出你目前所处区域各个部分的地图，有时还带标注。  x12
其他特工绘制了你当前所在这片区域各部分的地图，有时还带标注。    x10
```

改写时统一成一种，分叉一并消失。

## 两个根本性错误：折行规则一直算错了

### 第一次错：用纯贪心

第一版用纯贪心（累加到 240px 就换行）。引擎不是这样——当时我以为它走 `DialogueWrap.storyPages` → `PixelLayout`，于是第二次改成「优先断在合法边界，行首不能是标点」。

### 第二次错：误判「`DialogueWrap` 没接进游戏」

我只看了 `CorePatch.java`（那里只有一处 `terminalText` 注入），就推断 `DialogueWrap` 是纯测试用。核验方指出该看**候选产物**：

```
$ javap -v -classpath backup/cosmobreeder-multi.jar PRG.Nb | grep -c DialogueWrap
0
$ javap -v -classpath localization/builds/r9-polish-candidate54/cosmobreeder-multi.jar PRG.Nb | grep DialogueWrap
#249 = Methodref  PRG/DialogueWrap.story:(LPRG/aEO;)LPRG/aEO;
 198: invokestatic  #249  // Method PRG/DialogueWrap.story
```

`PRG.JR` 同理调 `DialogueWrap.radio`。**中文对话在发行产物里走 `DialogueWrap`，不走原版 `amw`。**

所以验收基准回到 `DialogueWrap` → `PixelLayout`：故事框 240px/story12，无线电 150px/bbc2。

### 原版是固定字符数硬切（记录，但不是基准）用仓库自带的 JDK 17 `javap` 逐层反编译 `PRG/amw`：

```
PRG.amw.a(String, amq)            // 切成行
  -> PRG.amr$e.a(String, String)     // 按 "<p>" 分段
  -> PRG.aDJ.e(String, int)          // 返回 aCj 迭代器
  -> PRG.aDI$a.p()                   // substring(c, c + cols)
  -> PRG.aDJ.a(String, int, int)     // 就是 String.substring
```

**没有像素测量，没有标点避让，没有词边界。** 每行固定若干个 UTF-16 字符，切在哪就是哪。

列数常量从各常量类的 `<clinit>` 读出：

| 常量 | 含义 | 值 |
| --- | --- | ---: |
| `PRG.Ol` | 故事框列数 | **28** |
| `PRG.Ob` | 无线电列数 | 20 |
| `PRG.NY` | 结局面板列数 | 12 |
| `PRG.Om` | 每页行数 | 3 |

`PRG.amw.b(char)` 只判断 ASCII 空格（`c == 32`），`PRG.amw.a(char)` 无条件返回空格——混淆层对「断点」的唯一概念是空格，而中文没有空格。

完整取证见 `wrap-rule-evidence.md`。

### 这解释了 batch-24 为什么必然失败

固定字数硬切下，只要句子长度不是列数整数倍，就**必然在某处被切开**，切点纯由字数决定。「把一处切词挪到别处」是这条路的固有性质，不是实现失误。

改文案仍有用，但作用方式不同：**不能消除切点，只能把切点移到标点后或虚词后**。

## 用引擎自己渲染（本批补上的工具）

前几版都在 Python 里复现折行规则，错了两次。这批补上了离线场景渲染：`tools/SceneRender.java` + `tools/scene_render.py` 直接加载候选 jar 里的 `DialogueWrap` / `DialogueGrid` / `PixelLayout`，让引擎自己算。

引擎实测行为（跑出来的，不是读出来的）：

- 满行 **20 个汉字**（12px × 20 = 240px）；
- **行首不出现标点**（`，`、`。`、`！` 被拉到上一行末尾）；
- 每页 3 行，不足补空；
- `formatCapped` 的 `q=28` 是 UTF-16 上限，对汉字文本不生效（20 < 28）。

全库 17,890 行渲染耗时 0.6 秒，**零引擎错误**。详见 [scene-render.md](scene-render.md)。

## 实测结果（引擎输出）

**这批最后只保留 22 行改动，73 行回退。** 原因是验收基准变了，见下。

| 范围 | candidate52（改前） | candidate54（改后） | 变化 |
| --- | ---: | ---: | ---: |
| 本批 96 行 · 故事框 240px | 91 处 | 35 处 | −56 |
| 本批 96 行 · 无线电 150px | 74 处 | 72 处 | −2 |

数字与早先 Python 复现的「950→901」不同：那是按跨行两字组合全量统计、包含断在完整词之后的情况；这里统计引擎实际输出。

### 为什么回退 73 行

反编译发现这批 96 行里有 **72 行位于 `<TomcatItems.*>` / `<BossuDex.*>` 条目下**，
它们走的是**无线电容器**（`PRG/JB → JM → JQ → JR → DialogueWrap.radio`，150px、
bbc2 10px、每行 15 汉字），不是 240px 故事框。按故事框验收的改善对它们不成立。

于是改按「两个容器都干净」重挑：

| 项 | 数量 |
| --- | ---: |
| 改前改后两边都干净 | 22 |
| 至少一边仍切词 | 73 |

回退那 73 行的实测依据：**没有一行能在无线电下改善**，反而有 **35 行会让无线电变差**。
所以保守取舍在两个容器下都是最优的。

详见 [simulated-render-research.md](simulated-render-research.md) 与
[real-scene-render.md](real-scene-render.md)。

## 判据的局限（必须说明）

引擎规则下，**只要断点落在两个汉字之间，就一定切开了某个东西**——这是中文排版的固有性质。要判断切开的是不是「词」，需要分词器。

本机没有分词器（不为此安装依赖），所以判据是频次代理：二字组全库出现 ≥30 次视为「稳固搭配」。这个代理会误报：`库里`（「机库里」的跨词）、`是真`（「全是真话」的跨词）、`们几`、`边有` 都被标出来，但它们不是词。

处理办法是把这些记为 `KNOWN_FALSE_POSITIVE` 并在文档说明，而不是悄悄放宽阈值。真正切开的词（`地图`109、`武器`、`太空海盗`、`进一步`、`撞到`、`东西`）都已修掉。

要精确判定必须引入分词，那是另一件事。

## 引擎改动

`editorial_repairs.py` 里 `line` 类型的守卫原本写成「断行符数量变化就要求文本逐字相同」，导致**任何整行改写都被拒**。而历史上 3,574 个 `line` 操作全是整行改写（R1～R9 的精校）。

守卫的本意是约束 batch-22/23 那种「插断行符」的改动，所以条件改成「断行符**增加**时」才检查。纯改写（断行符数量不变）不受这条约束。

## 复核修正

四路改写返回后逐条核对，多轮修回语义损失，典型几类：

- `很简单：你把外头找到的…` → 补回「在」：`很简单：你把在外头找到的花哨芯片带给我，`
- `无线电怎么也呼叫不通，偏偏你生命体征，又乱了套` → 标点错位，改为 `无线电呼叫怎么也接不通，你的生命体征又乱了套，我唯一收到的只有一阵发毛！`
- `在空中按 DOWN+JUMP 来俯冲。撞到东西就会弹起来` → 补回「如果」：`…就能俯冲。如果撞到东西，就会弹起来…`
- `其他特工绘制你当前所在区域各部分地图`（缺「了」，且第二行以「。」开头）→ `其他特工已经绘制了你所在区域各处的地图，有时还带标注。`
- `当初我们一开始就收到了…的报告，请了精神科医生！`（丢「还」，两个动作变成并列）→ `当初我们开始收到特工关于所谓的“精神力异能”的报告时，还请了精神科医生！`
- `我们已在旧机库雇好了一名本地的机械师了`（「了…了」重复）→ `我们在旧机库雇了一名本地机械师，能给你进一步的建议。`
- `以防万一，他说的都是真的`（逗号错位，原意是「以防他说的都是真的」）→ `以防他说的都是真的……`
