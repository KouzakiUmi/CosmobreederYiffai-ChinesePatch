## 阻断 3：折行规则算错了——成立，这是最要命的一条

第一版用纯贪心（累加到 240px 就换行）。引擎不是这样。核验方给出的机制是准确的，我在 `PixelLayout.java` 里核实到原文：

```java
private static boolean legalBoundary(String text, RawUnit left, RawUnit right) {
    ...
    return !contains("（［｛〈《「『【〔〖〘〚‘“([{", a)
        && !contains("、。，．：；？！‼⁇⁈⁉）］｝〉》」』】〕〗〙〛’”)]},.!?:;%‰…⋯", b);
}
private static boolean preferredBoundary(String text, RawUnit left, RawUnit right) {
    return !(word(a) && word(b));
}
```

`wrap()` 先填满，再取 `preferred`，其次 `legal`，都没有才强制断。

按这个规则重算，第一版有 **35 行根本没修好**——包括全部地图句：贪心给出 `…的地图 / ，有时还带标注。`（看着干净），引擎给出 `…的地 / 图，有时…`，因为 `，` 不能出现在行首，断点被往前挪，切开了「地图」（语料 109）。

**修法**：新增 `tools/engine_wrap.py`，把两套规则实现成共享模块，`assemble_rewrites.py` 改用之。按引擎规则重算后又暴露 14 行新问题，逐行调断点修到 0。

## 观察 1：59/96 是无线电、应量 150px——**我判断不成立**

核验方的依据是场景标签（如 `<TomcatItems.ZenerSquare>`）。但这个标签是**场景分隔标记**，标记后面的行是同一场景的对话，形如 `  Tomcat: [……]`，带说话人前缀和方括号。

判据在 `DialogueWrap.story` 里，它按 `StoryFont12.uses12(full)` 决定走哪条路径：

```java
public static boolean uses12(String fullCaption) {
    for (int i = 0; i < fullCaption.length(); i++) if (wide(fullCaption.charAt(i))) return true;
    return false;
}
```

`wide` 覆盖 U+1100–U+115F、U+2E80 以上的 CJK 区段等。本批 96 行的新文案**全部含汉字**（实测 `rows without any Han char: 0`），所以 `uses12` 全部为 true，全部走 `storyPages` → `DialogueGrid.format` → `PixelLayout`，即 240px / story12 / 3 行。

无线电是另一条路径：`DialogueWrap.radio`，`pixelWidth = columns == NY ? 80 : 150`，用于 `Ob`/`NY` 这两个 source-verified 的调用点。`datadf`/`datadm` 里的说话人对话不走这条。

**这条判断如果错了，整个批次就是有害的**——我实测过：按 150px/classic 算，本批让切词从 1,210 增到 1,249（**变差 39 处**）；按 240px/story12 算，从 950 降到 867（改善 83 处）。所以这个前提必须站得住，不能靠猜。

我把两条实测都留在这里，供后续核对：

| 容器规则 | candidate52（改前） | candidate54（改后） | 变化 |
| --- | ---: | ---: | ---: |
| 故事框 240px / story12 | 950 处 / 934 行 | 867 处 / 851 行 | **−83** |
| 无线电 150px / classic | 1,210 处 / 1,181 行 | 1,249 处 / 1,222 行 | +39 |

**未解决的部分**：我只能从代码路径推断，不能从运行态证实每一行实际走了哪条路径。要证实需要跑游戏或在测试里打点，本会话不做（不启动游戏）。这一条按「证据分层」记在未验证里。

## 观察 3：守卫对「断行符减少且改字」放开——成立

`editorial_repairs.py` 的 `line` 守卫现在是：

```python
if kind == 'line' and new.count(LINE_BREAK) > old.count(LINE_BREAK):
    if new.replace(LINE_BREAK, '') != old.replace(LINE_BREAK, ''):
        _fail('line break insertion must not alter the text')
```

所以「删掉 U+2028 同时改字」确实能过。核验方说得对。

我保留这个口子的理由：本批有 8 个 op 靠它落地（它们本来就是整行改写，没有 U+2028 可删）。核验方也确认历史上没有「断行符减少」的 line op，所以收紧不会影响任何已落地批次。

**这条需要决定**：收紧成「只要断行符数量变化就要求文本不变」会让本批那 8 个 op 失败，需要把它们改成不删断行符的写法。我倾向收紧——守卫的意义就是不给模糊地带。下一步做。

另外核验方指出 README 对 3,574 的解释不对（数字对）：确实，我说「旧条件会把它们全拒掉」是错的，其中 1,184 个是「断行符增加且文本不变」，旧条件本来就放行。已在 README 改正。
