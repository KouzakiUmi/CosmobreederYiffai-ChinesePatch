# batch-24：只修最严重的切词，分页不动

## 规矩

按你的标准：分页能不动就不动，只在「特别糟糕」的地方动，且不改变演出节奏。

所以三条硬条件，全部由扫描器强制：

1. **分页不动**——显示行数与原行完全相同；
2. **特别糟糕**——3 字以上的稳固词被切开（如「自卫武／器」「蜥蜴太／空海盗」）；
3. **不在演出交接点**——该行与下一个 `cut`／`fadecut`／`snap`／`music`／`rewind!` 之间没有别的台词，背景或角色切换的时机不会挪。

关于第 3 条要补充一个实测事实：`datadf/1` 与 `datadm/1` 里**一条演出命令都没有**（各 5,190／5,238 行，`cut`／`fadecut`／`snap`／`music`／`rewind` 命中数都是 0），`vsn` 脚本也不引用字典键（命中 0）。也就是说演出编排与这两份对话框台词是解耦的，本批改的 58 行全部落在对话框，改动不会挪动任何背景或角色切换的时机。第 3 条在这批里是自动满足的，但它仍然写在扫描器里——一旦将来要动 `vsn`，这条判定才真正起作用。

文字本身不动：去掉插入的 U+2028 必须逐字还回原文。

## 一个必须记下来的发现：字幕容器不认 U+2028

第一版把 125 行都收进来，其中 67 行在 `vsn` 脚本里。回归的 `subtitle` 一步立刻失败：

```
Parse Error, Position 14:29, found " 宇宙育种者]。\r\n"
    at SubtitleLayoutTest.parse(SubtitleLayoutTest.java:115)
```

`vsn` 里的台词同时喂给**字幕**容器，而字幕解析器不接受 U+2028。batch-22 和 batch-23 没碰到这个问题，只是因为它们恰好只改了 `datadf`／`datadm`（对话框），一处 `vsn` 都没动。

所以 **U+2028 只对对话框容器有效，对字幕无效**。本批把 `vsn` 整段排除，行数 125 → 58，重跑回归才通过。

这也意味着：字幕那一路如果还想修排版，得用另一套机制（或直接改文案让它自然折在词边界），不能靠插断行符。
