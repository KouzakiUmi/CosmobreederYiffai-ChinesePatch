# batch-23：折行不切词

## 为什么做这一批

引擎按像素贪心折行，不认词边界，所以一个词可能被拆到两行：

```
附近应该有一条传送管道，要是你有飞船，就      ← 「就」在行尾
能从那里登船！                              ← 「能」在行首，「就能」被切开
```

`PixelLayout` 把 U+2028 当显式断行，所以在词边界插一个就能把断点挪过去：

```
附近应该有一条传送管道，要是你有飞船，
就能从那里登船！
```

对照图 `out/layout/dialogue/wordbreak-before.png` / `wordbreak-after.png`。

## 三条硬条件

每行都要同时满足，扫描器和修复引擎各校验一遍：

1. **显示行数不变**。按**显示正文**量，不是物理行——说话人前缀（`  * `、`  Tomcat: `）不参与排版。这一条是 batch-22 踩过的坑：拿带前缀的物理行去量，会把「正文只有一行」的行误判成两行。
2. **去掉插入的 U+2028 后与原文逐字相同**。用 U+2028 而不是 LF，因为本工具链只在 CR/LF 处切行，行号不变，既有台账的行号引用全部有效。
3. **切词数必须严格减少**，不能把一处断词换成另一处。

另外不删任何**已有**断行：candidate51 里已有 batch-22 插的 U+2028，那些不是本批的改动对象，删掉会退回 batch-22 的成果。

## 判据与规模

「断点两侧的两个字构成常用组合」用**语料自身**的二元组频次做判据：该组合在全库出现 ≥8 次即视为一个词，断在这里算切词。这是频次代理，不是分词：

- 会漏掉低频专名（人名、地名、技能名）；
- 会把跨词的高频组合（如「的生」「样的」）误判为切词。

| 阶段 | 切词断点 | 涉及行数 |
| --- | ---: | ---: |
| candidate51（做之前） | 1,393 | 1,331 |
| candidate52（做完） | 180 | 168 |
| 本批修复 | 1,180 行／1,144 个新断行（这 1,180 行内切词 1,230 → 17） | — |

剩下 180 处分布在 168 行：多数是第一行严格占满 240px、词边界在 14 字搜索窗口之外，挪动会改变显示行数。

## 处置

全部 apply，理由一致：只挪断行位置，不动一个字。台账 `localization/translations/editorial-r9-batch-23-repairs.jsonl`（1,180 个操作），决策表 `review/decisions.tsv`，gate `review/build-gate.json`（`verified_for_application`）。

## 验证

- 逐条自查：1,180 个操作，文本零改动、显示行数零漂移、未删除任何已有断行、净插入 1,144 个断行。
- 修复前后都做了「会变差吗」的检查：**0 行把一处断词换成另一处**。第一版扫描器只取「第一个能让计数下降的走法」，有 43 行把一处高频断词换成了另一处（其中 4 行插进真词中间，「足／够」「使／出」）；改成对候选打分（先看消掉多少、再看引入多少新断点）后，这类交易为 0，本批 1,180 行内的切词从 1,230 降到 17。
- 17 步 CPU 回归：`tests/candidate52` 全部 exit 0。
- 明文读回：2,173 个操作 / 0 问题。
- 封签：`candidate52/acceptance.json`，39 批，status `passed_cpu_and_independent_review_not_real_clip_CRT_input`。
